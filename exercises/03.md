# Exercise 03

Exercises the checkout endpoint, which reserves stock in memory and persists a reservation.
It seems like concurrent checkouts go much slower than any single call.

```bash
cargo hotlap --exercise 03
```

Try the same workload at a higher rate, e.g. 100 req/s:

```bash
cargo hotlap --exercise 03 --rate 100 --reset
```

Note: requests still unfinished when the lap ends count as hotlap errors, they are
not necessarily HTTP error responses.

<details>
<summary>Hints</summary>

1. Persistence duration stays stable, so the dependency itself is not slowing
   down.

2. Compare `http.request`, `inventory.reserve`, and `inventory.persist`: 
why do reservation times grow while each persistence call stays near 45 ms?

2. Persistence spans never overlap, even for different products.

3. Check the usage of the mutex guard in inventory's `reserve` function.

</details>
