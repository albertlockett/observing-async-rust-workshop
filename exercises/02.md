# Exercise 02

This exercises the search endpoint, which we normally expect to be quite fast.
The client requests typeahead suggestions, roughly 5% of the time. 
So we expect that most searches should be fast. 
Instead, almost every search takes roughly 80 ms, why is this happening?

```bash
cargo hotlap --exercise 02
```

Review the trace for this run, can you spot anything helpful on the viewer?

## Part 1

The runtime trace tells us that requests are waiting, but it cannot name the
application operation they are waiting for. Add spans before attempting a fix.

First, enable Dial9's Tower integration in `workshop-app/Cargo.toml`:

```toml
dial9-utils = { version = "0.5", features = ["axum-08", "tower"] }
```

In `workshop-app/src/routes/mod.rs`, add these imports:

```rust
use axum::extract::{MatchedPath, Request};
use axum::response::Response;
use dial9_utils::dial9_span;
use dial9_utils::tower::Dial9SpanLayerWithResponse;
```

Then create a layer at the beginning of `router`:

```rust
let request_spans = Dial9SpanLayerWithResponse::new(|request: &Request| {
    let route = request
        .extensions()
        .get::<MatchedPath>()
        .map(|path| path.as_str().to_owned())
        .unwrap_or_else(|| "unmatched".to_owned());
    let (span, slots) = dial9_span!(
        "http.request",
        method = %request.method(),
        route: String = route,
        status: u64,
    );
    (span, move |response: &Response| {
        slots.status.set(u64::from(response.status().as_u16()))
    })
});
```

Add `.layer(request_spans)` to the router after `.with_state(state)`. This gives
every request an `http.request` span containing its method, matched route, and
eventual response status.

Now add child spans around these service operations:

- `Catalog::search` -> `catalog.search`
- `Catalog::refresh` -> `catalog.refresh`
- `Pricing::quote` -> `pricing.quote`
- `Inventory::available` -> `inventory.available`
- `Inventory::reserve` -> `inventory.reserve`
- `persist_reservation` -> `inventory.persist`
- `Recommendations::fetch` -> `recommendations.fetch`
- `Suggestions::fetch` -> `suggestions.fetch`

For an async operation, add these imports to its service file:

```rust
use dial9_utils::dial9_span;
use dial9_utils::span::Instrument as _;
```

Then wrap its existing body. For example, `Suggestions::fetch` becomes:

```rust
async {
    tokio::time::sleep(BACKEND_LATENCY).await;
    vec![format!("{query} gifts"), format!("{query} deals")]
}
.instrument(dial9_span!(
    "suggestions.fetch",
    query_len: u64 = query.len() as u64,
))
.await
```

For synchronous `Catalog::search`, also import
`dial9_utils::span::Span as _`, then create and enter the span before the
existing body:

```rust
let span = dial9_span!("catalog.search", limit: u64 = limit as u64);
let _entered = span.enter();
```

Because these spans execute inside `http.request`, the viewer can connect each request to its internal work.
Use stable operation names and useful scalar fields; avoid raw search terms or
request bodies. The solution patch contains the complete instrumentation if
you want to compare your version.
