# Solution 06

The application is healthy but CPU-starved by another process on the host.
During the middle band, application polls remain short and Tokio queues stay
without sustained buildup, while kernel scheduling delays rise to roughly
12–20 ms. Latency recovers as soon as the reporting job exits, without a code
change.

The fix is operational: isolate the workloads, reserve CPU for the service, or
cap and deprioritize the batch job. Making request handlers yield more often
would not create CPU capacity and is not the solution.
